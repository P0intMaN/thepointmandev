## 1. The Motivation

I have been lying to you.

Every time I wrote "the byte at address `0x1000`," I implied that address was a real physical location in a RAM chip. It isn't. It hasn't been, for any program, on any mainstream computer, for about forty years.

The addresses your program uses are fictions. They are translated — on every single memory access — by a dedicated hardware unit called the **Memory Management Unit (MMU)**, from the "virtual" address your program sees into a "physical" address that maps to actual DRAM. The translation has its own cache, called the **TLB** (Translation Lookaside Buffer). The translation can miss. When it does, your single `arr[i]` can stall for hundreds of nanoseconds while the CPU walks through four levels of tables in RAM just to find out where your data physically lives. If the page hasn't been backed by physical memory yet, the CPU traps into the operating system, and your "simple array access" disappears for microseconds. If the page was swapped to disk, it disappears for milliseconds.

This is not a niche concern. Virtual memory is the reason:

- Your program can address more memory than your machine physically has
- Two processes can't read each other's memory without being explicitly allowed
- `malloc` can return in a microsecond even when allocating gigabytes
- GC pause times in the JVM have the specific shape they do
- `-XX:+AlwaysPreTouch` exists as a JVM flag that serious production systems always set
- A null pointer dereference in Java becomes a `NullPointerException` through a mechanism that will surprise you

This is the last genuine machine-level lesson in Sub-course 0. After this: stack vs. heap, a brief assembly primer, and then we ascend into the JVM. Get your notebook.

## 2. The Problem That Invented Virtual Memory

Start here, because virtual memory is an engineering solution. You cannot appreciate the solution without seeing the pain it solves. It is 1970. There is no virtual memory. Every program uses physical addresses directly.

**Problem 1: Relocation.** Every program compiled in 1970 was compiled to assume it owned specific physical addresses — say, 0x0000 to 0xFFFF. If you wanted to run two programs at once, both expected to own address 0x1000. Only one physical address 0x1000 exists. Early operating systems "solved" this by recompiling programs with different base addresses before loading — a fragile, laborious process that broke whenever a program computed an address from another address at runtime.

**Problem 2: Protection.** Program A can read every byte of Program B's memory — its stack, its code, its private keys. A bug in A can overwrite B's code segment. A malicious A can steal from B. On a multi-user mainframe, this is an existential problem. One flawed program can corrupt every other program on the machine.

**Problem 3: Fragmentation.** Program A needs 30 KB. Program B needs 20 KB. Program C arrives and needs 25 KB. If A and B were loaded at non-contiguous addresses, the largest free contiguous block might be only 15 KB — even though 29 KB is free in total. C cannot run even though there's technically enough memory. Compacting running programs means moving them, which means patching every address they contain.

**Problem 4: Addressing more than you have.** A program wants to work with a 10 GB dataset. The machine has 4 GB of RAM. The classical answer was overlay files: manually load sections of the program into memory and swap them out when finished. This put the burden of memory management on the programmer.

Virtual memory solves all four simultaneously. The core idea — worked out on the Manchester Atlas by 1962 — is: give every process its own private, enormous, contiguous address space. Translate those private addresses to shared physical memory on the fly, in hardware.

Relocation: each process gets its own address space, so address 0x1000 means different things to different processes. No recompilation needed.

Protection: the OS controls the translation tables. A process can only access physical memory that its own tables map to. No mapping to process B's memory? No access. Hardware-enforced.

Fragmentation: physical memory can be divided into small fixed-size chunks and assigned to any virtual address. Non-contiguous physical chunks can appear as contiguous virtual addresses.

Addressing more than you have: virtual addresses that have no physical backing can be transparently loaded from disk on demand — the entire program image doesn't need to fit in RAM at once.

## 3. The Mental Model: Virtual Addresses, Physical Addresses, Pages

Here is what your hardware actually does every time your code touches memory.

Every process has its own **virtual address space**. On a 64-bit x86 machine, the address space is nominally `2^64` bytes — 16 exabytes. Current CPUs use only 48 bits (256 TB per process), and modern chips are extending to 57 bits (128 PB). Your process sees this entire space as its own. It does not know where other processes live. It cannot even see them.

When your code says `arr[i] = 42`, the compiler emits a store instruction with a virtual address. The MMU intercepts that address before it reaches the memory bus and translates it to a physical address — the actual row and column on a DRAM chip.

```
Source code:        arr[i] = 42
         ↓
Assembly:           mov [rax + rcx*4], 42    ← virtual address in rax+rcx*4
         ↓
MMU translates:     0x0000_7FFE_A3B2_C408    → 0x0000_0001_9842_3408
         ↓
RAM:                physical address 0x0000_0001_9842_3408 written
```

This translation happens on every memory access. Every load. Every store. Every instruction fetch. The CPU is incapable of touching physical memory without going through this step.

**Why translate at page granularity rather than byte by byte?** If you stored a mapping per byte for a 48-bit address space, the table would require `2^48 × 8 bytes = 2 petabytes` per process. Unusable. Instead, the MMU translates at **page** granularity: a page is a fixed-size block of virtual address space that maps to an equally-sized block of physical memory. The lower 12 bits of the address — the offset within the page — pass through unchanged. Only the upper bits (the virtual page number) are translated.

**Why 4 KB?** The page size of 4 KB (`2^12 = 4096` bytes) has been near-universal since the 1970s. It is an engineering compromise:
- Too small (e.g., 256 bytes): too many pages, page tables become enormous, TLBs (the translation cache) can't hold enough entries to matter.
- Too large (e.g., 1 MB): internal fragmentation wastes memory. A process allocating 5 KB needs 5 pages of 1 MB = 5 MB of physical memory to back them.

4 KB sits in the sweet spot. Linux, Windows, macOS, and essentially every modern OS default to 4 KB pages. (We will cover larger pages — huge pages — in section 8.)

<Quiz question="A 48-bit virtual address is 0x0001_A3B2_C408. The lower 12 bits are the page offset. What is the virtual page number? What is the page offset?">
  Lower 12 bits: `0x408 = 0b0100_0000_1000`. These are the offset within the 4 KB page — byte 1032 of its page. Upper 36 bits: `0x0001_A3B2_C` — this is the virtual page number, the index the MMU must translate. Only the VPN is looked up in the page tables. The PPN that comes back is concatenated with the unchanged offset `0x408` to produce the physical address.
</Quiz>

## 4. Page Tables: How Translation Is Stored

The MMU needs to know, for each virtual page number, the corresponding physical page number. This mapping is stored in **page tables** — a data structure in RAM.

A naive design would be a flat array: index by VPN, return PPN. For a 48-bit address space with 4 KB pages, there are `2^36` possible VPNs. At 8 bytes per entry, that is `2^36 × 8 = 512 GB` of page table per process. Obviously impossible.

The fix is a **multi-level page table** — a tree of small tables where most branches simply don't exist if the process hasn't mapped that region. On modern x86-64, the standard is **4-level paging**. The 48-bit virtual address is divided into five fields:

```
[ PML4: 9 bits ][ PDPT: 9 bits ][ PD: 9 bits ][ PT: 9 bits ][ Offset: 12 bits ]
```

Each 9-bit field indexes into a table of 512 entries (`2^9 = 512`). Four levels of 512-entry tables. To translate a virtual address, the MMU performs a **page table walk**:

1. The CR3 register holds the physical address of the PML4 table (the top level). This register changes on every context switch, because different processes have different page tables.
2. The top 9 bits of the virtual address index into PML4. The entry contains the physical address of the PDPT table.
3. The next 9 bits index into PDPT. The entry contains the physical address of the PD table.
4. The next 9 bits index into PD. The entry contains the physical address of the PT table.
5. The final 9 bits of the VPN index into PT. The entry contains the **physical page number (PPN)** — the answer.
6. Physical address = PPN concatenated with the low 12 bits of the virtual address.

Four memory accesses to translate one address. Before the data access itself. If each table entry is in RAM (cold), that is 4 × 100 ns = 400 ns of pure translation overhead — before you even touch the data you wanted. This would be catastrophic for every program on Earth.

It is tolerable because of the TLB.

## 5. The TLB: Caching the Translation

The **Translation Lookaside Buffer** is a small, fully-associative cache of recent virtual-to-physical page translations. It is physically separate from L1/L2/L3 (those cache data; the TLB caches translations). Every CPU core has one.

Typical TLB sizes:
- **L1 TLB (per core):** 64–128 entries for 4 KB pages, separate for instructions and data
- **L2 TLB (per core):** 1024–2048 entries, unified

Each entry stores a VPN and its corresponding PPN (plus permission bits). Lookup is parallel across all entries — fully associative, like a small content-addressable memory.

**TLB hit (the fast path):** The VPN is found in the TLB. Translation completes in 1 cycle. No page table walk. This is the case for nearly all accesses in a typical program.

**TLB miss (the slow path):** The VPN is not in the TLB. The MMU walks all four levels of the page table. The translation result is placed into the TLB for future use. Cost depends on where the page table entries are:

```
Table entries in L1 cache:   4 × 1 ns  =   4 ns
Table entries in L2 cache:   4 × 4 ns  =  16 ns
Table entries in L3 cache:   4 × 12 ns =  48 ns
Table entries in RAM:        4 × 100 ns = 400 ns
```

In a typical program with good spatial locality, the page table entries that cover the hot working set are themselves hot in the regular data cache — so TLB misses cost 10–50 ns, not 400 ns. But for workloads with large, sparse working sets — random access into a multi-gigabyte data structure — both the data cache and the page table entries are cold, and every access pays the full 400 ns translation overhead on top of the RAM access cost.

**The hit rate.** In typical programs, TLB hit rates are above 99%. This is why the four-memory-access overhead is acceptable — it is almost never paid. Programs exhibit strong page-level locality: you touch the same pages repeatedly, just as you touch the same cache lines repeatedly. The TLB exploits this the same way L1 exploits cache-line temporal locality.

## 6. Page Faults: When Translation Cannot Succeed

Sometimes the page table walk finds... nothing. The entry says "not mapped." The CPU cannot complete the access from the tables alone. It takes an exception — a **page fault** — and traps into the operating system's fault handler.

There are three kinds of page fault, and their costs are orders of magnitude apart.

**Minor fault (soft fault).** The virtual page is backed by something the OS knows how to provide — a freshly allocated page that hasn't been physically set up yet, or a shared mapping that can be satisfied from the page cache. The OS allocates a physical page (possibly zeroed), updates the page table entry, and resumes your program. Your `arr[i]` eventually completes.

Cost: **1–10 microseconds**. Fast by page fault standards. One thousand to ten thousand times slower than a cache hit.

**Major fault (hard fault).** The page was swapped out — evicted from physical RAM to disk to make room for other processes — or it is part of a memory-mapped file that hasn't been loaded yet. The OS must read the 4 KB page from disk, place it in physical RAM, update the page table, and resume your program.

Cost: **~100 µs on NVMe SSD, 1–10 ms on spinning disk**. A single "memory access" that looks like `arr[i]` can take longer than a network round trip.

**Segmentation fault.** The virtual address isn't mapped at all — the process is accessing memory it has never allocated and has no right to. The OS sends `SIGSEGV`. Most programs crash. In Java, the JVM registers a signal handler that intercepts `SIGSEGV` at address 0 and converts it to a `NullPointerException`. This is not a catch-all; the JVM only handles faults from addresses near null. An out-of-bounds array access is caught differently (bounds check on the index). But null dereference in Java is, at the machine level, a page fault from address 0 or a small offset therefrom, caught by the JVM's signal handler before the process crashes.

  The JVM relies on the OS's memory protection. Virtual address 0 (null) is intentionally left unmapped in the process's page tables — any access to it or a small range above it generates a SIGSEGV signal from the hardware. The JVM registers a custom signal handler at startup. When SIGSEGV fires from address 0 (or a low offset), the handler constructs a NullPointerException and throws it into the Java stack. This is faster than a conditional check on every field access — it costs nothing on the non-null fast path and only activates on the faulting case. The OS hardware does the check for free.
</Quiz>

## 7. The Lazy Allocation Trick

Here is something that surprises most engineers. When you call `malloc(1_000_000_000)` or Java's `new byte[1_000_000_000]`, the allocator does not find 1 GB of free physical RAM and reserve it. It cannot — that would take hundreds of milliseconds of OS work, and most allocations are never fully used.

Instead, the OS records that the virtual address range is "allocated" — it updates its virtual memory bookkeeping — and returns immediately. **No physical memory is touched.** The mapping is marked "valid but not backed."

When your code subsequently writes to a byte in that allocation, the CPU looks up the page in the page table, finds a "not yet backed" entry, and takes a minor page fault. The OS allocates a physical page (zeroing it first, for security — you must never receive another process's discarded data), updates the page table entry, and resumes your code. This is the first touch.

The next access to any byte in that 4 KB page is a TLB hit. No fault. But the next page — the next 4 KB — is still "not yet backed." The minor fault happens again when you first touch it.

Consequence: if you allocate a 1 GB array and immediately traverse it sequentially, you will pay one minor page fault per 4 KB — that is **262,144 page faults**, each costing 1–10 µs. That is 0.25 to 2.5 seconds of fault-handling overhead hiding inside what looks like array initialization in your code. This is called the **first-touch latency** problem and it is one of the most common sources of mysterious startup slowness in Java services.

The OS also zeroes physical pages before giving them to your process. This is not optional — leaking another process's memory contents would be a security catastrophe. The zeroing happens either lazily (at first touch) or eagerly (the OS maintains a pool of pre-zeroed pages). Either way, you pay for it.

## 8. `-XX:+AlwaysPreTouch`: Paying Upfront

The JVM flag `-XX:+AlwaysPreTouch` tells the JVM to touch every page of the heap at startup by writing a zero byte to each one. This forces all minor page faults — and the associated OS work of allocating and zeroing physical pages — to happen once at startup rather than spread across runtime.

```bash
# Without AlwaysPreTouch: fast startup, mysterious runtime latency spikes
java -Xmx8g MyService

# With AlwaysPreTouch: slower startup, predictable runtime latency
java -Xmx8g -XX:+AlwaysPreTouch MyService
```

What changes:
- **Startup time increases** by the time it takes to touch all 8 GB. At ~1 µs per 4 KB page, that is `8 GB / 4 KB × 1 µs = 2,097,152 µs ≈ 2 seconds` of additional startup time per GB of heap.
- **Runtime latency becomes predictable**. There are no longer page fault spikes during execution. The heap is fully backed before the service accepts requests.
- **Memory usage appears immediately in `top`/`htop`** rather than growing gradually. This surprises operators who monitor RSS.

Every serious low-latency Java service — high-frequency trading, low-latency databases, real-time systems — enables this flag. The alternative is paying 1–10 µs at unpredictable moments during the request path when the JVM first touches a previously-unallocated heap region.

A related flag: `-XX:+AlwaysPreTouch` only helps with heap pages. For off-heap buffers (`ByteBuffer.allocateDirect`), you need to manually touch pages yourself, or use OS-level pre-allocation.

## 9. Huge Pages: The TLB Escape Hatch

The L2 TLB on a modern CPU holds 1024–2048 entries, each covering 4 KB. That is 4–8 MB of addressable virtual space before TLB misses start. For programs with working sets in the gigabytes — databases, JVMs with 64 GB heaps, in-memory analytics — this coverage is grossly insufficient. TLB misses become a significant fraction of execution time.

Modern CPUs support **huge pages**: pages larger than 4 KB. Two common sizes:

- **2 MB huge pages (Linux: "huge pages", Windows: "large pages"):** Each TLB entry covers 2 MB instead of 4 KB — 512× more coverage. A 2048-entry TLB holding 2 MB entries covers 4 GB of working set instead of 8 MB.
- **1 GB huge pages:** Each entry covers 1 GB. Used for truly enormous working sets (database buffer pools, ML model weights).

The JVM can be told to use huge pages:

```bash
java -Xmx64g -XX:+UseLargePages MyService
```

This requires the OS to have pre-allocated huge pages (Linux: `vm.nr_hugepages` sysctl; Windows: "lock pages in memory" privilege). The JVM will use 2 MB pages for the heap if available.

**The downside: fragmentation.** A huge page is allocated all-or-nothing. If you allocate a 2 MB huge page and put 100 KB in it, 1.9 MB is wasted. More critically, the OS needs contiguous 2 MB regions of physical memory. On a machine that has been running for days, physical memory is fragmented — finding 512 contiguous 4 KB pages is harder than it sounds. The OS may fail to allocate huge pages when asked.

**Transparent Huge Pages (THP).** Linux has a feature called THP that automatically promotes 4 KB pages to 2 MB when it detects a contiguous region. THP sounds attractive but has a troubled reputation. When THP decides to defragment memory to create a huge page, it blocks the process for milliseconds. MongoDB, Redis, Cassandra, Elasticsearch, and many other databases explicitly recommend disabling THP (`echo never > /sys/kernel/mm/transparent_hugepage/enabled`) for exactly this reason — the latency spikes THP causes are worse than the TLB benefits it provides.

For the JVM specifically: use explicit huge pages with `-XX:+UseLargePages`, configured at OS level, rather than relying on THP. The JVM's huge page support is explicit and predictable; THP's is opportunistic and can cause GC pauses to extend unpredictably.

| Scenario | Total cost |

| TLB hit + L1 hit | ~1 ns |

The bottom of this table is 7 orders of magnitude below the top. That is the same span I opened Lesson 0.5 with — the range from "one cycle" to "a full-blown I/O operation." When a memory access is slow, it is slow for a reason on one or both axes.

## 11. The Analysis: What This Means for Your Code

**Large array first-touch.** When you write `new long[100_000_000]` (800 MB), allocation is instant — no physical pages are committed. When you subsequently iterate the array for the first time, you pay one minor page fault per 4 KB — `200,000` faults at 1–10 µs each = 200 ms to 2 seconds of hidden latency during what looks like simple iteration. Subsequent traversals are fault-free. Use `-XX:+AlwaysPreTouch` to push this cost to startup.

**Memory-mapped files.** `FileChannel.map()` maps a file into virtual address space. No data is loaded. Sequential access over a mapped file triggers minor faults (page-cache hits) at ~1 µs each — tolerable because the OS prefetches pages ahead of your sequential scan. Random access triggers faults for each 4 KB page at 100 µs–10 ms each — potentially catastrophic. For random-access workloads over large files, explicit read-ahead or a database with a buffer pool is almost always better than mmap.

**TLB pressure.** The L2 TLB covers 4–8 MB at 4 KB page size. If your working set exceeds this and you access it randomly (hash table probing, B-tree traversal, sparse graph traversal), TLB misses compound with cache misses. Every access pays 50–400 ns of translation overhead on top of the cache miss cost. This is the main reason large in-memory databases benefit so much from huge pages — they eliminate TLB pressure for the buffer pool entirely.

**GC and swap.** When the JVM's GC moves objects, it touches many pages. If any of those pages were swapped out, the GC pause time grows by the time to bring them back from disk — potentially seconds rather than milliseconds. This is why the JVM documentation says "do not swap your JVM heap." Production JVMs typically configure the OS to disable swap (`vm.swappiness=0` on Linux), or lock the heap in physical memory (`mlockall`). A GC pause that should be 20 ms can become 5 seconds if the GC touches swapped pages.

**Context switches.** When the OS switches from one process to another, it loads the new process's CR3 register — pointing to its own page tables. This invalidates the TLB entirely, because the TLB entries from the old process are now meaningless. The new process starts with a cold TLB and pays misses on every page it touches. This is one reason multi-threading (shared address space, no TLB flush on thread switch) is faster than multi-processing (separate address spaces, full TLB flush on context switch) for workloads that context-switch frequently.

## 12. The Proof: Why Multi-Level Page Tables Scale

Claim: a 4-level page table for a 48-bit address space uses far less memory than a flat table, even in the worst case.

**Flat table memory cost:** `2^36 VPNs × 8 bytes = 512 GB` per process. Impossible.

**4-level tree memory cost.** Each table has 512 entries × 8 bytes = 4096 bytes — exactly one page. The tree has four levels. In the worst case (every virtual address mapped), you need:

```
Level 4 (PML4):      1 table  =       4 KB
Level 3 (PDPT):    512 tables = 2,048 KB = 2 MB
Level 2 (PD):   512² tables  =   1 GB
Level 1 (PT): 512³ tables    = 512 GB
```

So the worst case is still 512 GB — same as the flat table. But this is the worst case: every possible virtual address mapped. That never happens. A real process maps perhaps a few GB of virtual space: code, heap, stack, shared libraries. Most of the 256 TB virtual address space is unmapped and has no page table entries at all.

In practice, a process with a 64 GB heap and 1 GB of code/stack uses perhaps 1 GB of PT entries (64 GB ÷ 4 KB pages × 8 bytes = 128 MB of PT tables, plus much less for higher levels). The total page table footprint is typically a tiny fraction of the process's actual memory usage.

The deeper insight: the multi-level structure lets non-existent mappings cost nothing. A region of virtual space that is entirely unmapped requires only the single higher-level entry that says "nothing here" — no lower-level tables exist. This is what makes sparse virtual address spaces practical.

## 13. The Trade-offs

**Virtual memory adds overhead, unavoidably.** Every memory access requires a TLB lookup. TLB misses require a page table walk. The overhead is usually invisible — TLB hit rates above 99% make the per-access cost negligible. It becomes visible when working sets are large and sparse.

**Swap is disaster for latency-sensitive workloads.** A major page fault is 100 µs to 10 ms. At p99 or p99.9, even rare swap events destroy tail latency. For any service with latency SLAs, disable swap or lock the heap in memory. The performance trade-off is clear: lose some physical memory flexibility, gain predictable latency.

**Huge pages: use explicitly, not transparently.** For large heaps (>8 GB), configure huge pages at OS level and tell the JVM with `-XX:+UseLargePages`. Do not rely on THP. Measure TLB miss rate before and after — on large-heap services, 10–20% of CPU time in TLB misses is common without huge pages.

**NUMA and virtual memory.** On multi-socket servers, RAM is attached to specific CPU sockets (Non-Uniform Memory Access). A thread on socket 0 accesses RAM on socket 1 at roughly 2× the latency. The OS's virtual memory system maps physical pages to physical RAM, and if it maps them to the wrong socket, every access pays the NUMA penalty. `-XX:+UseNUMA` tells the JVM to allocate object regions on the NUMA node local to the thread that allocated them. This is a separate (and important) performance lever for large multi-socket servers.

**Real systems:**
- **Linux's `mlock` / `mlockall`:** pins pages in physical RAM, preventing swap. Used by databases, JVMs, and real-time systems. Must be combined with sufficient physical RAM — locking 64 GB of heap on a 64 GB machine leaves nothing for the OS.
- **Elasticsearch** recommends `bootstrap.memory_lock: true`, which calls `mlockall` to prevent the heap from being swapped. Without this, a GC on a swapped heap can produce multi-second pauses.
- **Java's `-XX:+AlwaysPreTouch -XX:+UseLargePages`** combination: standard configuration for low-latency trading systems. Eliminates both first-touch faults and TLB pressure.
- **Redis** recommends disabling THP: `echo never > /sys/kernel/mm/transparent_hugepage/enabled`. The THP defragmentation pauses are directly visible as p99 latency spikes in Redis benchmarks.
